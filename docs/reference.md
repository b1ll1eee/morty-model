# เอกสารอ้างอิง morty-model

รายละเอียดที่ README ตัดออกเพื่อความกระชับ อ่านเมื่อต้องปรับแต่งหรือแก้ปัญหา

## ติดตั้ง Ollama แบบไม่ใช้ Homebrew

```bash
mkdir -p ~/.local/ollama ~/.local/bin
curl -fsSL -o /tmp/ollama.tgz https://github.com/ollama/ollama/releases/latest/download/ollama-darwin.tgz
tar -xzf /tmp/ollama.tgz -C ~/.local/ollama
ln -sf ~/.local/ollama/ollama ~/.local/bin/ollama
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.zshrc && source ~/.zshrc
```

## ที่เก็บโมเดลและการตั้งค่าความเร็ว

Ollama เก็บ weight ไว้ที่ `~/.ollama/models` โดยปริยาย เครื่องนี้ย้ายไปดิสก์ DEV เพื่อไม่กินพื้นที่ในเครื่อง

```bash
echo 'export OLLAMA_MODELS="/Volumes/DEV/models/ollama"' >> ~/.zshrc && source ~/.zshrc
ollama serve &
```

โฟลเดอร์ข้างเคียง `/Volumes/DEV/models/lora/` และ `mlx/` สำรองไว้สำหรับ adapter และโมเดลแปลงรูปแบบในอนาคต
ตรวจความคืบหน้าดาวน์โหลดด้วย `du -h` บนไฟล์ `*-partial` ไม่ใช่ `ls -l` เพราะ Ollama จองขนาดเต็มไว้ก่อน

## เปิด Ollama อัตโนมัติตอน login (LaunchAgent)

ไฟล์ `~/Library/LaunchAgents/com.morty.ollama.plist` รัน `~/.local/bin/ollama serve` พร้อมตัวแปร
`OLLAMA_MODELS=/Volumes/DEV/models/ollama` และ `OLLAMA_KEEP_ALIVE=1h` (ถือโมเดลไว้ใน RAM 1 ชั่วโมง ไม่ต้องโหลดซ้ำเวลาสลับ 7b กับ 14b)
log อยู่ที่ `~/Library/Logs/morty/ollama.log`

```bash
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.morty.ollama.plist   # เปิดใช้
launchctl bootout   gui/$(id -u)/com.morty.ollama                                 # ปิด
launchctl print     gui/$(id -u)/com.morty.ollama | grep -E "state|pid"           # ดูสถานะ
```

ตัวแปรเพิ่มเพื่อความเร็วและ RAM (ตั้งใน LaunchAgent และ `~/.zshrc`): `OLLAMA_FLASH_ATTENTION=1` เร็วขึ้นบน Apple Silicon,
`OLLAMA_KV_CACHE_TYPE=q8_0` ลด RAM ของ context ลงราวครึ่งโดยคุณภาพแทบไม่ต่าง, `OLLAMA_MAX_LOADED_MODELS=2` ถือ 7b กับ 14b พร้อมกัน,
`OLLAMA_KEEP_ALIVE=1h` ไม่ต้องโหลดซ้ำเวลาสลับ profile

ข้อควรระวัง: process ที่ launchd เปิดไม่ได้รับสิทธิ์เข้าถึงดิสก์ภายนอกเหมือนโปรแกรมที่เปิดจาก Terminal
ครั้งแรก macOS จะถามสิทธิ์ "ollama ต้องการเข้าถึงไฟล์บน removable volume" ถ้าไม่กดอนุญาต server จะค้างตอนเปิดไฟล์และไม่ตอบ request
ถ้าไม่เห็นกล่องถาม ให้ไปที่ System Settings → Privacy & Security → Files and Folders (หรือ Full Disk Access) แล้วเพิ่ม `~/.local/ollama/ollama`
จนกว่าจะอนุญาต ให้เปิด server เองจาก Terminal ด้วย `ollama serve` ซึ่งอ่านค่าจาก `~/.zshrc` อยู่แล้ว

## ไฟล์ profile

แต่ละ profile เป็นไฟล์ TOML ใน `morty/profiles/`

| ฟิลด์ | ความหมาย |
|---|---|
| `title` | ชื่อที่แสดงในหน้าแชท |
| `system` | system prompt ของ expert ด้านนั้น |
| `model` | (ไม่บังคับ) ใช้โมเดลคนละตัวกับ `.env` เช่น `qwen3:14b` |
| `data_dir` | (ไม่บังคับ) โฟลเดอร์เอกสารสำหรับ RAG เช่น `data/dev` |
| `[options]` | พารามิเตอร์ส่งให้ Ollama: `temperature`, `num_ctx`, และ `think` (ปิดโหมดคิดยาวของ qwen3) |
| `[rag]` | `enabled`, `top_k` จำนวนท่อนที่แนบ, `min_score` ความคล้ายขั้นต่ำ |

ค่าที่ส่งตรงๆ ตอนรัน (`--model`, `--system`) มีสิทธิ์เหนือกว่าค่าใน profile เสมอ
ตั้ง profile เริ่มต้นได้ที่ `MORTY_PROFILE=` ใน `.env`

## RAG ทำงานอย่างไร

`morty/rag.py` ทำดัชนีไฟล์ข้อความและโค้ดใน `data/<profile>/` ด้วย `nomic-embed-text`
(ใส่ prefix `search_document:` ตอนทำดัชนี และ `search_query:` ตอนค้น ตามที่โมเดลต้องการ)

- ตัดเป็นท่อนละราว 1,200 ตัวอักษรตามย่อหน้า มี overlap 150 ตัวอักษร
- เก็บดัชนีที่ `data/<profile>/.morty-index.json` ไฟล์ที่ sha1 ไม่เปลี่ยนจะไม่คำนวณซ้ำ
- ตอนถาม ค้นท่อนที่คล้ายที่สุด `top_k` ท่อนที่คะแนนถึง `min_score` แนบไปกับคำถามพร้อมหมายเลข [n]
- แนบเฉพาะข้อความที่ส่งรอบนั้น ไม่เก็บลง history ของแชท เพื่อไม่ให้ context บวม
- cosine similarity คำนวณด้วย Python ล้วน พอสำหรับหลักพันท่อน ใหญ่กว่านั้นค่อยย้ายไป vector DB

เกณฑ์ `min_score` ของ dev คือ 0.6 เพราะวัดแล้ว nomic ให้คะแนน 0.45 ถึง 0.56 แม้คำถามไม่เกี่ยวกับเอกสารเลย
ลองดูคะแนนจริงได้ด้วย `python -m morty.rag search dev "คำถาม"`

## รูปแบบ eval

`evals/<profile>.jsonl` หนึ่งบรรทัดต่อหนึ่งข้อ

```json
{"id": "py-json", "q": "คำถาม", "expect_any": ["คำที่ควรมีอย่างน้อยหนึ่งคำ"], "expect_all": ["คำที่ต้องมีทุกคำ"], "thai": true}
```

การตรวจเป็นแบบหาคำในคำตอบ ไว้จับการถดถอยเวลาแก้ prompt หรือสลับโมเดล ไม่ได้แทนการอ่านคำตอบจริง
ผลแต่ละรอบเก็บที่ `evals/results/` (ไม่ commit) และ `--models a,b` จะสรุปตารางเทียบให้

สองตัวเลือกที่ทำให้ eval น่าเชื่อถือขึ้น

- `--judge` ให้โมเดลกรรมการ (ค่าเริ่มต้น `qwen3:14b` เปลี่ยนด้วย `--judge-model`) อ่านคำถาม คำตอบ และคำใบ้ แล้วให้คะแนน 0 ถึง 2 ตาม rubric
  (2 ถูกครบ, 1 ถูกบางส่วน, 0 ผิด) ผ่าน structured output จึงได้ JSON เสมอ คะแนนนี้แยกจากการหาคำ ใช้จับคำตอบที่ "มีคำที่ถูก แต่เนื้อหาผิด"
  และคำตอบที่ถูกแต่ใช้คำอื่น กรรมการเป็นโมเดลเล็กจึงยังพลาดได้ ให้ดูเหตุผลที่มันเขียนเมื่อให้คะแนนต่ำกว่า 2
- `--repeat N` รันแต่ละข้อ N รอบ รายงานว่าข้อไหนผ่านทุกรอบ ตกทุกรอบ หรือแกว่ง (flaky) ก่อนเชื่อความต่าง 1 ข้อระหว่างสองโมเดล
  ควรรู้ก่อนว่าความแกว่งของโมเดลเดียวกันอยู่ที่กี่ข้อ ไฟล์ผลจะมี `-xN` ต่อท้าย

ตัวอย่าง: `python -m morty.evaluate dev --judge --repeat 3`

## structured output

pipeline ของ reviewer (finding แต่ละรอบ และคำตัดสิน KEEP/DROP) กับกรรมการของ eval ส่ง JSON schema ไปกับคำขอผ่าน `format` ของ Ollama
โมเดลจึงต้องตอบตาม schema ไม่ต้องพึ่ง regex อ่านข้อความ ถ้าได้ข้อความที่ไม่ใช่ JSON (โมเดลเก่าหรือ backend อื่น) โค้ดถอยไปอ่านรูปแบบบรรทัด `[bug] ...` และ `N: KEEP ...` แบบเดิมโดยอัตโนมัติ
schema อยู่ใน `morty/reviewpipe.py` (`FINDINGS_SCHEMA`, `VERIFY_SCHEMA`) และ `morty/evaluate.py` (`JUDGE_SCHEMA`)

## pipeline ของ reviewer

`morty.review` (ค่าเริ่มต้น) ไม่ได้ถามโมเดลรอบเดียว แต่ทำตามลำดับใน `morty/reviewpipe.py`

1. **analyzer** รัน `ruff` (กฎ E9, F, B, S) และ `bandit` บนไฟล์ Python ที่เกี่ยว ผลถือเป็น finding ที่ยืนยันแล้ว
   คลาสบั๊กที่เครื่องมือจับได้ (ชื่อตัวแปรไม่มีจริง, mutable default, shell injection, secret) จึงไม่หลุดแม้โมเดลพลาด
   ถ้าเป็น `--diff` จะรันบนไฟล์ .py ที่เปลี่ยน ถ้าเป็นโค้ดจาก stdin จะเขียนไฟล์ชั่วคราวให้
2. **ตรวจ 4 รอบแยกหัวข้อ** ความถูกต้อง, ความปลอดภัย, ความทนทาน, style รอบละ 1 คำขอ บอกโมเดลว่าอะไรถูกพบแล้วไม่ต้องซ้ำ
3. **ตรวจซ้ำ** ส่ง finding ระดับ bug/risk ทั้งหมดกลับไปให้โมเดล (temperature 0) ตัดสินทีละข้อ KEEP / DOWNGRADE / DROP
   เกณฑ์คือต้องยกอินพุตที่ทำให้พังจริงได้ ยกไม่ได้ถอน
4. **รวมผล** ตัดซ้ำตาม (บรรทัด, ระดับ) analyzer ชนะเสมอ บรรทัดเดียวกันเก็บเฉพาะระดับที่หนักที่สุด เรียง bug → risk → style

โหมด: ค่าเริ่มต้น = โมเดลรอบเดียว + ผล analyzer แนบท้าย (1 คำขอ) · `--pipeline` = เพิ่มตรวจซ้ำ (3 คำขอ) · `--quick` = รอบเดียวไม่มี analyzer
(โหมด 4 รอบแยกหัวข้อถูกถอดออกแล้วหลังวัดว่าไม่เพิ่ม recall แต่ช้า 5 เท่า ผลการวัดยังเก็บไว้ด้านล่างเพื่ออ้างอิง)
ดูตารางผลวัดและเหตุผลของค่าเริ่มต้นในหัวข้อ "ผลเทียบโมเดล"
วัดด้วย `python -m morty.evaluate reviewer --pipeline` เทียบกับรอบเดียว

## เครื่องมือของ dev (tool calling)

profile ที่มี `[tools] enabled = true` จะได้เครื่องมือเหล่านี้ ทำงานได้เฉพาะใน workspace (โฟลเดอร์ที่รัน `morty.chat` หรือ `--workspace`)

| เครื่องมือ | ทำอะไร | ถามก่อน |
|---|---|---|
| `read_file` | อ่านไฟล์พร้อมเลขบรรทัด (ครั้งละไม่เกิน 400 บรรทัด) | ไม่ |
| `list_dir` | ดูไฟล์ในโฟลเดอร์ ข้าม .git .venv node_modules | ไม่ |
| `search_code` | ค้น regex ทั้งโปรเจกต์ ได้ ไฟล์:บรรทัด | ไม่ |
| `git` | เฉพาะคำสั่งอ่าน: status diff log show blame branch ls-files | ไม่ |
| `run_command` | รัน shell ใน workspace timeout 60s | ใช่ |
| `run_python` | รันโค้ด Python สั้นๆ | ใช่ |
| `edit_file` | แทนที่ข้อความ old → new ในไฟล์ (old ต้องพบครั้งเดียว) แสดง diff ก่อน | ใช่ |
| `write_file` | สร้างไฟล์ใหม่หรือเขียนทับทั้งไฟล์ แสดง diff ก่อน | ใช่ |

ลำดับที่ prompt ของ dev สั่ง: read_file → edit_file เป็นหลัก, write_file เฉพาะไฟล์ใหม่ (ไฟล์เดิมต้องระบุ overwrite=true)
และหลังแก้ให้อ่านซ้ำหรือรันเทสต์ยืนยัน ทุกเครื่องมือแก้ไฟล์ถูกกันไม่ให้ออกนอก workspace เหมือนตัวอื่น และ `--yes` จะข้ามการถาม (ไม่แนะนำกับการแก้ไฟล์)
ไม่มีการสำรองไฟล์อัตโนมัติ: diff ที่แสดงตอนถามคือจุดตรวจสุดท้าย และ git ของโปรเจกต์คือทางย้อนกลับ

eval การแก้ไฟล์: `evals/dev-edit.jsonl` 5 ข้อ รันด้วย `--workspace-template evals/fixtures/edit` ซึ่งคัดลอกโฟลเดอร์ต้นแบบเป็น workspace ใหม่ทุกข้อ
ตัวตรวจดูสภาพไฟล์จริงหลังทำงาน (`expect_file`: contains / not_contains) ไม่ใช่แค่ข้อความคำตอบ

- สร้างไฟล์ใหม่อัตโนมัติ: จบ eval ทุกครั้งจะเขียน `reports/dashboard.html` เสมอ ส่วนการบันทึก log และการให้คะแนน (`/bad`, `/good`, `morty.log rate`)
  จะเขียนใหม่เฉพาะเมื่อไฟล์มีอยู่แล้ว เพื่อไม่สร้างไฟล์ให้คนที่ไม่ได้ใช้ dashboard ทุกกรณีถูกห่อด้วย try/except ไม่ทำให้งานหลักล้ม

## Log การใช้งาน

`morty/log.py` บันทึกทุกคู่ถามตอบจากแชทและ review ลง `logs/YYYY-MM-DD.jsonl` แบบ append อย่างเดียว (ปิดด้วย `MORTY_LOG=0`)
eval ไม่ถูกบันทึกเพื่อไม่ให้ปน

```json
{"type": "exchange", "id": "a1b2c3d4e5f6", "ts": "...", "source": "chat", "profile": "dev", "model": "qwen2.5:7b",
 "question": "...", "answer": "...", "seconds": 12.3, "refs": ["morty-project.md#2"]}
{"type": "rating", "ref": "a1b2c3d4e5f6", "ts": "...", "rating": "bad", "note": "ตอบเป็นอังกฤษ"}
```

| คำสั่ง | ทำอะไร |
|---|---|
| ในแชท `/bad เหตุผล`, `/good` | ให้คะแนนคำตอบล่าสุด |
| `python -m morty.log rate <id> bad "เหตุผล"` | ให้คะแนนย้อนหลัง (id แสดงท้ายผล review) |
| `python -m morty.log show [-n 50] [--profile dev]` | รายการล่าสุด |
| `python -m morty.log bad` | เฉพาะที่ติดธง bad พร้อมคำถามและคำตอบ |
| `python -m morty.log to-eval dev` | แปลงเคส bad เป็นบรรทัด eval ให้ไปเติม `expect_any` |
| `python -m morty.log stats` | จำนวนต่อ profile และโมเดล พร้อม good/bad |

log ชุดนี้คือชุดข้อมูลตั้งต้นของ LoRA fine-tune ในอนาคต คู่ที่ติดธง good ใช้เป็นตัวอย่างสอน คู่ที่ติดธง bad ใช้เป็น eval

## หน้าจอ TUI (`morty` / `morty ui`)

สร้างด้วย Textual อยู่ใน `morty/ui.py` ใช้สมองเดียวกับ `morty chat` ทุกอย่าง (RAG, เครื่องมือ, log, rating) ต่างกันที่การแสดงผล

- งานกับโมเดลรันใน thread แยก (`@work(thread=True)`) หน้าจอจึงเลื่อนดูและพิมพ์ต่อได้ระหว่างรอ
- การขออนุญาตจาก thread ใช้ `threading.Event` รอผลจาก `PermissionScreen` (modal) ซึ่งแสดง diff ด้วย syntax highlight และรับ y/n หรือปุ่ม
- คำตอบที่ไม่ใช้เครื่องมือ stream ทีละชิ้นลง Static แล้วแทนด้วย Markdown ที่เรนเดอร์แล้วเมื่อจบ
- Ctrl+C ตั้งธงยกเลิก: การ stream หยุดทันที ส่วนการเรียกเครื่องมือที่ค้างอยู่จะเสร็จก่อน (Ollama ไม่มีทางยกเลิกคำขอกลางคัน)
- `--yes` อนุญาตทุกอย่างอัตโนมัติ ใช้เฉพาะงานที่ไว้ใจ
- เทสต์รันแบบ headless ด้วย `app.run_test()` ครอบคำสั่ง / การ stream และกล่องขออนุญาต

## เรียกจาก Python

```python
from morty import llm

llm.ask("สรุปข้อความนี้ให้หน่อย ...")                        # profile general
llm.ask("อ่านไฟล์ JSON ใน Python ยังไง", profile="dev")      # system prompt + RAG ของ dev
llm.ask("...", profile="dev", rag=False, model="qwen3:14b")  # ทับค่าได้ทุกอย่าง
llm.chat([{"role": "user", "content": "สวัสดี"}])          # ส่งบทสนทนาเต็ม
llm.embed(["ข้อความ 1", "ข้อความ 2"])                      # เวกเตอร์สำหรับค้นหา
```
